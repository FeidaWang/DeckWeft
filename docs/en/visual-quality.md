# Browser quality and bounded correction

[简体中文](../zh-CN/visual-quality.md) · [Evidence](../evidence/vis-010/review.md)

1. Use Node 22+ and an independently installed Playwright QA module. Point `CHROMIUM_PATH` at an isolated testing browser outside `/Applications`; set `PLAYWRIGHT_MODULE` to its module path. Installed browser bundles and personal profiles remain read-only. These are optional development tools, not runtime dependencies.
2. Run `npm run visual:verify -- --case release-gallery`. This representative local case builds six complete 15-scene stories: both languages with three interaction themes. The original cover, evidence and chapter retain their authored themes. It does not certify the broader release gallery or any host application.
3. Run `npm run visual:review`. Open the printed loopback URL. Choose an interactive HTML output, open the complete-story sheet, and inspect native scene images and explored states. Results live in `dist/visual-quality`. No remote service, model or image request is made.
4. Read `report.json`. It includes per-region source/text coverage, exact chart values, actual platform font diagnostics, image decoding, console diagnostics, before/after action traces and structured issues. Boxes use document CSS pixels at the captured viewport. Global errors and missing geometry explicitly have null bounds. Source coverage means the original reference remains available in output; it does not verify a citation's truth. Clipping and contrast use current DOM/SVG geometry; repeated composition means more than three adjacent identical composition contracts. This heuristic needs visual judgment for subtler repetition.
5. Inspect the images themselves. Contact sheets establish whole-story rhythm; native components establish legibility. Full-page images establish reading order and responsive flow. A hash, successful DOM test or screenshot creation does not mark a visual review complete.
6. Save an array of explicit review objects to a separate JSON file. Each object needs `receiptId`, `reviewer`, `delivery` (how actual images were received), `images` (actually viewed filenames), `judgment`, `issues`, and `verdict` (`pass` or `fail`). Required images are marked `reviewRequired`; other native scenes remain available for additional review. Visual issues need `sceneId`, `nodeId`, `bounds`, `severity`, `reason`, and `suggestion`. See the recorded review file in the evidence folder for an example.
7. Run `npm run visual:verify -- --review /absolute/path/review.json`. The gate passes only after machine checks and a current explicit image review both pass. The tool checks current source/contract/theme/harness hashes, output bytes and image bytes before recording review. A custom project file is also checked for changes.

For your own v3 project, pass `--project /absolute/project.json --home /absolute/local-library`. Existing v1/v2 workflows keep their separate renderer and storage; this tool never migrates or repairs them silently. Recheck after editing content, exact data, sources, layout, assets, viewport, interaction state or renderer. `receiptCurrent` compares the project and captured observation; a receipt covers only its recorded states, not future audience exploration. Re-run capture for new states. Review attestations are accountable records, not technical proof that a person or model actually looked.

Automatic correction is deliberately narrow: only an affected scene's composition can change. The original document, data, sources, assets, stable identities, crops and unrelated scenes stay intact. Author composition locks are enforced. Contrast, source, missing-asset and broken-interaction issues stop for explicit scoped work; the tool does not invent missing content, unlock authors or hide a failure with an image of the whole page.

The default repair budget is **two rounds, six measured candidates, two accepted scene changes and 60,000 ms per story**. Set `--max-rounds`, `--max-candidates`, `--max-scene-changes`, or `--max-ms` to reduce budgets. More than two automatic rounds are refused. The controller rejects late results and signals cancellation; an external evaluator must honor its abort signal to release resources promptly. It never promotes late or incomplete work. Browser processes are closed on completion/failure. Candidate time and rejection reasons remain in the report.

If the gate fails, inspect `repair.candidate`, `repair.attempts`, diagnostics and pending review state. Candidate HTML files remain available. A previously passed run is copied to `accepted/<receipt-id>/` before a new capture; `repair.artifact` points to that saved output when repair fails. Without a previous passed artifact, the report says so and retains the supplied source. Repair never saves into your library, bypasses revision conflicts, or changes history. Recover content using the normal revision browser, then recapture. Keep the evidence folder to preserve previous receipts and screenshots.

The representative checks cover chart filtering, diagram/code explanation, image comparison/hotspots, replay/seek, keyboard and native touch events at 390/1024/1440 CSS pixels with reduced motion. They are not exhaustive accessibility, alternate-engine, font-environment, host or native-export certification. Full-resolution scenes and HTML exports retain editable DOM/SVG; only the QA contact sheet uses screenshot thumbnails.
